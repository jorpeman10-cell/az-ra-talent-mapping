# 猎头用工决策引擎 —— HR 工具化开发文档

> 版本：v1.0（评审稿）
> 目的：评估将现有"猎头顾问用工决策模型"产品化为 HR 工具的可行性
> 目标场景：内部人才调薪 / PIP 管理 / 晋升评估 + 外部候选人定岗定薪参考
> 现状代码：`workspace/headhunt_model/`（已跑通全链路，10 名在职顾问实测）

---

## 一、产品定位与场景拆解

### 1.1 当前工具是什么

一个**基于真实经营数据的顾问产能-成本决策引擎**：从谷露系统自动采集回款/签约/面试/客户数据，叠加财务真实薪酬成本，输出每个顾问的 EMPLOY / INCUBATE / PASS 决策、3 年 NPV/IRR、以及薪资承受极限。

### 1.2 目标 HR 场景与差异分析

| 场景 | 输入 | 输出 | 与当前引擎的差异 |
|---|---|---|---|
| **内部调薪** | 在职顾问 ID | 薪资上调极限月薪、调薪建议区间 | ✅ 已实现（于肖肖案例：4 档产能口径 × 薪资扫描） |
| **PIP 管理** | 在职顾问 ID | 是否达 PIP 解除标准、观察期触发条件 | ⚠️ 半实现：有产能/成本判据，缺"PIP 目标线"配置和过程指标阈值体系 |
| **晋升评估** | 在职顾问 ID | 产能分位、稳定性、独立获客力（α）评分 | ⚠️ 半实现：画像四维度齐全，缺晋升职级映射规则 |
| **外部定岗定薪** | 候选人简历信息（无内部历史） | 建议职级、薪资带宽参考 | ❌ 缺核心模块：候选人无回款历史，需要"行业分位数 × 画像推断"的另一条估计路径 |

**关键结论：内部三个场景是现有引擎的直接延伸（1-2 周工作量）；外部定岗定薪是新产品模块（需要外部市场薪酬数据库）。**

## 二、现有系统架构（已实现，v7.1）

```
数据采集层 (step2_collect.py)
  ├─ 表A 顾问季度回款      invoiceassignment ⋈ invoice(status='Received')
  ├─ 表B 顾问客户关系      client.addedBy_id 判定 SELF/COMPANY
  ├─ 表C 项目明细          offersign ⋈ joborder (成单周期/费率)
  ├─ 表D 公司季度汇总      invoice 聚合 + 成单周期/费率
  ├─ 表E 年度目标          report_revenue_annual_target (无年份, 仅当前年)
  ├─ 表F 在途签约管道      offersign Accepted ± invoice 去重, >100万/单截断
  └─ 活动量               jobsubmission(推荐) + clientinterview(面试) 按季聚合

清洗层 (step3_cleaning.py)
  3σ异常插值 / 缺失季度补零 / 单位统一(万) / 新顾问保护期 / 离职标记 /
  公司序列插值 + 环比同比

外部数据层
  ├─ salary_loader.py    底薪+职位工资+津贴 (salary_detail.csv)
  ├─ cost_loader.py      社保率实算 + 管理公摊按人头均摊 (2026成本拆分.xlsx)
  └─ scenario_external.py 外部行业 slope 情景 (医药猎头赛道: -0.05~+0.05)

计算引擎 (step4_engine.py + headhunt_model_irr20.py)
  Step1 画像: μ=max(4Q,8Q均值), CV=min(回款CV,面试CV), β收缩=1+(β-1)R², α=SELF占比
  Step2 市场: slope(近2季YoY均值) + mcv → RISING/FALLING/FLAT/VOLATILE
  Step3 交互: 有效基数 = max(μ×4, 近12月签约×回款率) × max(0.2, 趋势因子-波动惩罚)
             保守产能 = 有效基数 × (1 - min(0.6, CV×0.5 + mcv×0.3))
  Step4/5 财务: 雇员/孵化双模式, 季度现金流, NPV按季折现, IRR按季年化
             门槛: 首年利润率≥15% 且 IRR≥20%

输出层 (step5_run.py → output/)
  单顾问决策 JSON (106个) + 批量排名看板 JSON + 薪资极限扫描
```

### 实测性能指标

- 数据规模：106 名历史顾问 / 10 名在职 / 23 个季度公司序列
- 回测精度：留出 4 季度 MAPE 69.5%（个人级回款预测的结构性噪声下限，ramp-up 顾问误差最大）
- 活动指标预测力：面试数领先回款 2 个季度（r=0.39）；活动CV vs 回款CV r=0.82
- 已修复的口径缺陷：α 重复计数、CV 双算、β 噪音（全员 R²=0 自动收缩）、回款滞后低估、双重折减 bug、期初垫全年成本

| 数据 | 来源 | 更新方式 | 产品化注意 |
|---|---|---|---|
| 回款/签约/面试 | 谷露 MySQL（SSH 隧道） | 可定时每日 | 需从生产只读账号拉取，现有 `debian-sys-maint` 不合规 |

| 外部行业 slope | 猎聘/科锐财报、智联报告 | 季更人工录入 | 文档已附数据源清单和估计方法 |
| 候选人薪酬分位 | **无** | **需采购/爬取** | 外部定岗定薪的前置依赖 |

### 已知数据质量问题（产品化必须处理）

1. offersign 单笔签约录入错误（540万 案例）→ 已加 100万/单截断 + outlier 告警
2. offer↔invoice 一对多导致重复计数 → 已按 jobsubmission 去重
3. 成本表"公积金"列口径存疑（算出 81-89% 社保率，于肖肖月均 1.06万 超月薪）→ 待财务确认
4. 合并行/重名（沈铭骋/曹迎奥、刘科利/李彩霞、魏菲×2）→ 当前跳过，需 HR 拆分归属
5. 谷露目标表无年份 → 历史预算校准不可用，irr20 calibration 回退默认值

## 四、HR 工具化差距与模块设计

### 4.1 模块 M1：调薪工作台（改造现有，工作量小）

- 输入：顾问 ID → 自动带出画像 + 4 档产能口径
- 输出：薪资扫描曲线（当前于肖肖脚本的产品化）：EMPLOY 极限月薪 / 盈亏平衡月薪 / 建议调薪区间
- 新增：**调薪对赌规则配置**（如"Q4 回款≥15万 则次年调至 X"），自动生成考核触发器

### 4.2 模块 M2：PIP / 晋升评估（半新建，公司已有成文制度）

**制度资产盘点**（已全部读取，数据均可对接谷露）：

| 文件 | 位置 | 核心内容 |
|---|---|---|
| `绩效管理政策及薪酬激励政策 管理层版/顾问版 2023.pptx` | 微信文件 | **提成阶梯**：≤40万→30% / 40-60万→32% / 60-100万→35% / 100-150万→38% / 150-200万→40% / >200万→45%；**提成=税后回款×比例−已发基础薪资**（季度按30%预提、年底按实际比例补差、成本滚动不清零）；税后系数93.6%；团队管理奖金 5-7%；大客户奖金 2-4%；业绩分配 客户开发10%/对接20%/候选人管理55%/推荐15% |
| `10-Par绩效及薪酬激励政策--宋小丽.docx`（2021.12 生效） | iCloud 晋升确认信/ | **PIP 明文条款**：季度 Offer 业绩未达 Baseline 或绩效未达要求 → 公司有权发出 PIP；**Baseline = 3×月基础工资（含职位工资）**；PIP 期间暂停发放职位工资；PIP 后仍无改善 → 协商降职降级，公司保留终止雇佣权利。OKR：半年平均达成率<60% 晋升顺延一季，连续 3 个月<60% 当年不得晋升 |
| `晋升机制.pptx.pdf`（2021 修订稿3.0） | D盘 效能产品/ | 职级年度开票目标：ACT 30万→ECON 120万；升职线=半年开票（C1→SC1 需 60万+BD 2家客户），最多连升3级；管理线需培养下级+路演+2个月密集考核 |
| `积分晋升体系.docx`（2019，访寻员线） | D盘 人力资源体系/ | 积分=开票/300+KPI×3±行为分；季度评级 300/600/700/900 分 + **电话量1000通/季必要条件**；**连续两季<300分→列入待安排序列**（PIP 触发原型） |
| `绩效考核体系2.0.docx` | 同上 | 流程 SOP：财务每月按谷露数据统计 KPI、每季度统计 offer、最低绩效分值→绩效工资核算 |
| `猎企提点晋升政策 250609.xlsx` | D盘 AI辅助机器人/ | **竞品对标情报**（嘉驰/VIP/CGP/慧永等），非内部制度 |

**对模型的两个即时影响**：

1. **引擎 tier() 与官方提成阶梯完全一致**（30/32/35/38/40/45%）——交付代码的提成参数已与制度对齐，无需调整
2. **但引擎成本公式与制度不符**：官方提成=税后回款×比例**−已发基础薪资**（即总现金薪酬≈回款×比例，底薪含在内），而引擎当前是"底薪+社保+提成（回款×tier）"叠加，对高业绩顾问**双重计算了底薪**。这导致 EMPLOY 模式成本被系统性高估——修正后赵婉玉级顾问的雇员 NPV 会显著改善。建议按制度公式改为：`现金薪酬 = max(底薪, 税后回款×tier)`，提成部分 = 超出底薪的部分

**系统对接设计**：

- **PIP 触发器（按制度原文）**：季度 Offer 业绩（开票）< 3×月基础工资 → PIP 建议；PIP 期间停发职位工资（薪资模型需支持"PIP 状态"标记，于肖肖案例即此情形）；连续 2 季积分<300（访寻员线）→ 待安排序列
- **职级目标线在线化**：职级/年度/季度目标、升职线、BD客户条件配置进后台，不再依赖 PDF
- **晋升自动跟踪**：滚动 6 个月开票 vs 升职线自动比对（含连升级数测算）；BD 客户数用表 B 自动核验；OKR 达成率纳入晋升资格校验（半年均值<60% 顺延）
- **口径注意**：制度用**开票/税后回款**，模型产能用回款——invoice 表 sentDate/paymentReceivedDate 均有，增加开票口径半年滚动聚合即可
- **新人保护期**：与清洗层"入职<2季度不参与 β/α"及积分制"3 个月扶植期"对齐
- **晋升评分卡**（辅助路演评审）：产能分位 40% + 稳定性 min-CV 20% + 独立获客 α 20% + 客户结构 20%
- **合规红线：系统只输出"建议"，PIP/晋升/淘汰决策必须人工签署，留存人工 override 日志**

### 4.3 模块 M3：外部定岗定薪（全新建，工作量最大）

候选人无内部数据，估计路径完全不同：

```
候选人输入: 目标公司/职级/年限/过往业绩声明/期望薪资
    ↓
映射内部标杆: 我司同职能顾问的 μ/CV/成本 分位数表（P25/P50/P75）
    ↓
外部校准: 医药行业薪酬分位数据（需采购: 美世/怡安/智联分位报告, 或从谷露
          candidate.current_salary/expected_salary 25万条简历自建分位数）
    ↓
输出: 建议职级 + 薪资带宽(P25-P75) + 该候选人入职后的盈亏平衡产能线
```

**隐藏优势：谷露 candidate 表有 `current_salary`/`expected_salary` 字段（候选人简历数据），可自建医药猎头赛道的人才薪酬分位数据库——这是竞品没有的资产，建议优先验证数据覆盖率。**

### 4.4 模块 M4：配置后台（文档第六章 Task 3 的落地）

- 难度趋势曲线 / 目标利润率 / IRR 门槛 / 公摊口径（人头 vs 权重）/ 外部 slope 季度录入
- 所有当前硬编码在 `DEFAULT_CONFIG` 的参数在线化

## 五、技术架构建议（产品化形态）

```
前端 (HR 操作台)
  ├─ 顾问看板（现有 ranking board JSON → Web 表格）
  ├─ 单人详情页（画像雷达图 + 产能瀑布图 + 薪资扫描曲线）
  └─ 候选人录入页（M3）

API 服务 (FastAPI)
  ├─ /advisor/{id}/decision   单顾问决策
  ├─ /advisor/{id}/salary-scan 调薪扫描
  ├─ /board/ranking           批量看板
  ├─ /candidate/benchmark     外部定薪（M3）
  └─ /config                  参数后台

计算层: 现有 Python 引擎原样封装（step2-5 + irr20）
数据层: 谷露只读从库 + 本地 Postgres 缓存（现有 raw_cache 机制升级）
任务调度: 每日增量同步 + 季度外部数据录入提醒
权限: HR 可见成本/决策, 业务线长仅可见产能画像, 薪酬列脱敏分级
```

**不建议重写的部分**：计算引擎的 7 轮口径修正（v1→v7.1）全部经过真实数据验证，直接封装为服务即可，重写风险远大于收益。

## 七、风险与合规

1. **劳动法风险**：PIP/淘汰相关输出必须定位"决策参考"而非"自动决策"，保留完整人工审批链和日志
2. **薪酬数据安全**：成本/薪资数据分级权限，操作留痕；外部候选人模块不含内部员工薪资明细
3. **模型误差披露**：个人级预测 MAPE ~70%，所有输出必须带置信度标签（现有 confidence 字段：HIGH/MEDIUM/LOW）和建议区间而非点值
4. **数据依赖**：谷露生产库的只读账号与同步稳定性是 P0 前置条件
5. **小样本**：在职仅 10 人，决策阈值的统计意义有限，前 3 个月建议"模型建议 + 管理层复核"双轨运行
